Carribrary privacy notice
Updated October 30, 2026

Publisher: Chezburber Studios
Privacy contact: chezburbermerch@gmail.com

Your library
Carribrary is a phone companion for a library server you or your household operate. Books, borrower names and optional contact details, loans, due dates and borrowing requests are stored on that server. Paired phones can view and administer that library. The app sends library changes to your server over an encrypted connection and verifies the paired server identity. Device names and cryptographic pairing credentials identify approved phones. The publisher does not operate a hosted library service in this version.

On your phone
The app keeps an encrypted library cache for viewing while offline, encrypted pending changes for retrying, and preferences and pairing information. Private cryptographic keys are held in Android Keystore. Camera access is optional and requested when scanning. Barcode and QR recognition runs on the phone; camera frames are not uploaded by Carribrary. You can type codes instead. Carribrary does not read your address book or send texts automatically. Optional server email reminders and password recovery are described below.

External services
Book-detail lookups send the ISBN to Open Library. When you search for a cover, the app sends the ISBN and book title/author to your library server. Google Books is optional; when configured, the server can send book identifiers/title/author to Google for on-demand results. Google-sourced image requests and attribution links contact Google. No Google API key is bundled with the companion. The server queries Open Library and, when a matching item is available, Internet Archive. Borrower information and loan history are not sent to these providers. Cover images are fetched from the selected provider or the cover URL stored with a book. Providers receive the requested URL and normal network information, including the IP address of the server for server lookups and of the phone for image requests. Their policies apply to these requests.
Google ML Kit provides barcode recognition. It can report device/app information, installation identifiers, performance and scanner events to Google for diagnostics and usage analytics. Carribrary adds no advertising or separate analytics service. See Google's ML Kit disclosure and privacy information at https://developers.google.com/ml-kit/android-data-disclosure and https://policies.google.com/privacy .

Sharing you choose
A public book-list link exposes catalog details and availability to people with the link. Borrower contacts and private loan history are not shown on that list. Requesters may send a name, contact information and message to the household server through its request form. Library administrators can review those requests. You can disable public sharing.
Preparing a borrowing receipt hands the selected recipient and receipt text to your chosen messaging/email app; you decide whether to send it. That service's policies apply. Exporting a backup or book list saves or shares it at your direction. JSON backups include private borrower and loan details; protect them and share them only as intended.

Retention and deletion
The household controls the server and its backups. Removing a borrower or book with history may archive it to preserve loan records rather than erase that history. Ask the household administrator about removing retained records and backups. Forgetting the phone connection removes its pairing and encrypted library/pending/share caches; it does not delete the server's library. Clearing Android app storage or uninstalling removes app-local data, but previously exported files remain until you delete them. Revoking a phone on the server stops further access. The publisher cannot delete a library hosted on your computer. Google and other service providers apply their own retention policies.

Support and changes
Do not send borrower records, private pairing QR codes or backups when requesting support unless you deliberately choose to share them. This policy will be updated if the app's data handling changes. Contact Chezburber Studios at chezburbermerch@gmail.com for software privacy questions. Contact your librarian for records stored on their server.

Household reading and private borrower reading
Unlinked household reading profiles are administered by librarians and included in library backups and authorized phone caches. Borrower account personal reading, TBR, notes and wishlists use the separate encrypted private-list system described below. The old personal reading links are not a substitute for a private borrower account. Reading progress never returns a physical book automatically.

Borrower sign-in accounts
Visitors can register a username, password, name and optional contact details through an enabled shared library page. The household server stores salted password hashes, approvals, account-to-reader/borrower links and hashed session/recovery tokens in a separate private credential database. Passwords are not stored in plaintext or included in library exports. Account approval and explicit linking are required to access existing borrowing history. Approved sessions can view only their own loan and reading history and submit requests. The browser uses Secure, HttpOnly, SameSite=Strict session cookies lasting up to one day. Password recovery uses one-use, time-limited links. A librarian can issue a reset link. If the owner enables email recovery and configures SMTP, a borrower can request a link to their saved email; that provider receives the address and reset message. Reset requests do not disclose whether a username exists. Resetting a password ends existing sessions. Blocking an account ends its sessions and revokes its linked personal reading QR. Accounts and session data stay on the household server; the publisher does not host sign-ins. The household controls retention and access.


Optional due-date reminders send the borrower name, book details and due date through the library owner’s configured email provider, only after the librarian records permission. SMTP credentials are encrypted in the private server folder and excluded from library JSON exports. Delivery-attempt metadata is stored separately. Deleted books/borrowers remain recoverable in the Recycle Bin until the owner removes that recovery entry; records needed for loan/reading history remain archived. Windows pre-update safety copies contain the complete private database and key material and must be kept private.


Account deletion is available through My data & privacy in the borrower browser app and through the library owner in Borrower accounts. Account-only deletion removes current sign-in credentials/session/reset records and revokes linked personal reading QR access while retaining operational library records; the current encrypted personal vault is removed. Full personal-information deletion additionally removes explicitly linked/selected borrower and reading profiles, reading notes, requests and returned-loan history; active books must first be returned. Other guest requests sharing contact details are deleted only if selected. This bypasses the Recycle Bin and does not make a pre-deletion backup. The owner can optionally delete all installation-managed automatic/safety backups; exported copies, other backups, emails and offline caches may retain older information. New registration with a deleted username starts pending without inherited access. This is logical application deletion, not guaranteed forensic disk erasure.


The optional borrower Home screen web app stores public branding/preferences and the last shared catalog path in browser local storage. It uses the existing secure account cookie for sign-in, where applicable. Its network-only service worker does not cache borrower profiles, contacts, loans, notes, credentials or API responses for offline use. Installing does not grant extra access. Chrome/browser-managed installed-app metadata and previously exported/offline copies remain subject to the browser/device and owner controls.

Browser companions and optional push: Browser admin pairing uses a separate protected, expiring, revocable session. The iPhone and borrower PWAs do not cache private API responses for offline use. Their browser stores normal sign-in cookies, public name/color branding and the last public catalog path. Custom library icons and book descriptions are public. On-demand descriptions use Open Library and, when configured, Google Books with only book identifiers. Web Push is off until the user opts in and grants browser permission. Subscription endpoints/keys and VAPID keys are protected on the server. Apple/Google/Mozilla/Microsoft push services see endpoints and timing; empty push messages contain no book titles, contact info or reading notes. Workers display generic reminders or request alerts. Unsubscribe, sign-out, account block/deletion or browser revocation stops the corresponding subscriptions. Native Android supports optional periodic request alerts, distinct from PWA Web Push. Email reminders and tap-to-send texts remain separate. Browser/OS permission and delivery settings apply.

Android native administrator alerts: Settings & Tools → Borrowing & Reminders → Background notifications, then grant notification permission. Android polls the paired server about every 15 minutes, subject to battery/OS scheduling; these are not instant push. Existing pending requests are the initial baseline. Generic alerts open Requests; disable or Forget connection cancels them. No PWA or Firebase account is needed; only request-ID hashes are kept for deduplication.


Borrower data controls
Borrowers can sign in and use My data & privacy to clear completed history or delete their own sign-in account and linked information after a preview, password check and typed username confirmation. The librarian has the same administrative deletion tools. Full information deletion requires resolving outstanding physical loans; sign-in deletion alone remains available and retains library records, which is disclosed before confirmation. Ask the library owner to resolve retained records and private backup copies. No automatic remote wipe of disconnected devices is promised. /account/delete-help on the library HTTPS address provides the browser-only path and support instructions. The software publisher does not operate these household databases.
Completed-history clearing preserves active loans, holds and unfinished reading, uses a preview and typed confirmation, and does not create a new copy of erased history. It removes matching private idempotency receipt copies; older private backups, exports and messages are separate. Device cache clearing does not erase server data or pairing. This version does not implement whole-catalog borrower offline downloads.


Encrypted personal lists
Borrower personal TBR/reading records, ratings, notes and private wishlists are encrypted in the borrower’s browser with a separate private passphrase and a random recovery code. These secrets and raw private-list encryption keys are not sent to Carribrary Server or saved in browser storage by Carribrary. The server stores an account-bound encrypted document. Administrative state, phone caches and library exports exclude borrower personal reading. Unlinked household reading profiles remain admin-managed and visible to paired admins. Shelf locations and the household Books to buy acquisition list are admin-only and excluded from borrower/public projections.
Requests/messages intentionally sent to the librarian, loan/due-date history, account identity and service metadata remain operational server records. Login password resets do not decrypt a private list. Losing both the private passphrase and recovery code makes the personal contents unrecoverable. Owners can export/restore an encrypted personal backup with their own secret. Both account-deletion scopes remove the current encrypted vault; export it first if desired. Administrative library JSON/scheduled library snapshots are not backups of borrower vaults or credentials; a complete server backup or the borrower’s encrypted export is needed.
Legacy plaintext reading records move into encryption during explicit borrower setup: ciphertext is stored before the current plaintext/associated receipts are erased. Previous backups, exports and device copies may still contain older unencrypted information. No retroactive encryption or remote wipe is promised. The server delivers the browser application, so an actively malicious or compromised host could modify it to capture future secrets; this feature is not protection from a malicious app host and has not received an independent security audit.

Windows recovery points: administrator-protected historical snapshots are
separate from live account deletion and ordinary library backup cleanup. The
library owner removes them using Update and recovery → Delete recovery points.
Compatible program recovery keeps current account/vault/deletion state; it does
not restore a historical database. External copied backups cannot be recalled.

Complete server-data backups: an authorized librarian can download a password-encrypted archive of current administrative records, sign-in/account storage, encrypted borrower vaults, server identities/keyrings and saved settings. Borrower vaults remain independently encrypted; this does not reveal personal reading to admins. The librarian controls archive storage and password; Carribrary cannot reset a forgotten archive password. Copies can retain information deleted later. Temporary snapshots stay in the protected server data folder and are removed after normal completion/failure; an interrupted machine may require cleanup. External HTTPS/proxy material, OS service/tasks, environment-only settings and historical backups are separate.

Complete snapshot recovery warning: Restoring an earlier complete snapshot rewinds account deletions, passwords, device revocations and lending history. Review accounts and paired devices before making the restored server reachable. Compatible program-only recovery keeps current data instead.

Optional copy labels contain the selected book title, visible catalog number, library name and an opaque permanent copy reference. They contain no account, pairing or sharing access secret. Labels and PDFs are created locally and saved or printed only when an administrator chooses. Dispose of obsolete labels and exported PDFs as appropriate.

Optional registration verification: if a server administrator enables Cloudflare Turnstile, the registration browser loads Cloudflare resources and the server sends the challenge token and client IP to Cloudflare for validation. Carribrary does not include passwords, names, contacts or private reading/vault data in that verification request. The default configuration uses local attempt limits and librarian approval without contacting this provider. The site key is public; the secret is deployment configuration kept server-side.

Optional complete-backup verification uploads a user-selected encrypted archive and its password only to the paired Carribrary server. Protected temporary decryption checks file hashes and databases; normal completion/failure removes temporary files. Server crashes can require administrator cleanup. Verification never restores live records, and the developer receives no backup or password.

Complete Backup Recovery runs as a separate local operating-system launcher. It temporarily decrypts a selected archive for verification and isolated testing, and can replace live data only after explicit confirmation. It retains the entire previous data folder privately and pauses historical remote access/automatic messaging until local review. Finish removes normal temporary test/staging data, not retained current/failed folders or original archives; crash remnants can require cleanup. No backup/password is sent to the publisher.

New complete backups use portable password-encrypted key copies for replacement-computer recovery; live key protection is unchanged. Optional unattended seven-day backups store the archive password protected on the household server, retain four managed completed archives and never send archives to the publisher. Downloaded copies are controlled by the owner. Automatic catalog snapshots retain sixteen scheduled and seven daily files; manual/migration copies are separate. Historical restores pause notifications, automatic backups and remote access for local review. Old Windows archives may still be machine-bound; borrower personal vaults still require their separate private secret.

Optional aggregate analytics contains no visitor identity/IP/search text/private reading data. Daily buckets retain 730 days and all-time totals remain until cleared. Public browser DNT/GPC preferences suppress telemetry. Personal progress/sessions/goals/quotes/page notes remain in borrower encrypted vaults.

Purchase suggestions
Anyone with an enabled shared-library link, or an approved account, may submit a book/series title, optional author/ISBN and a short reason for the librarian to consider buying it. No name, contact field or account association is stored by this feature. Do not include personal/contact information or private reading notes in the reason. Suggestions are operational messages to the library administrators, separate from encrypted personal reading lists, and are encrypted at rest on the household server. No suggestion data is sent to book-lookup providers or the software publisher. Administrators can consider, decline or permanently delete suggestions. The current server retains at most 500 entries; retry receipts contain hashes/IDs only and are bounded. Complete backups can retain older suggestions; library-only JSON exports exclude them. Because suggestions are not associated with an account, deleting that account does not identify or remove them: ask the librarian to delete a particular suggestion. Optional admin alerts use generic messages without titles or notes.

Optional borrower self-service, library cards and kiosks
The librarian independently enables self-checkout, self-return reports and kiosks; all start off. Authenticated borrowers can use permitted circulation tools. A self-return report records a pending physical receipt until a librarian confirms the book arrived. Card identifiers, protected PIN verifiers, station credentials, circulation records and security attempt counters stay on the household server. A card QR is a credential: keep it private. Cards alone cannot open personal encrypted reading. Kiosk sessions show only the authorized borrower's necessary circulation information and should be ended after use. Authorized staff can issue/revoke cards and stations. Card printing and PDFs are owner-controlled local exports. Complete backups retain card/PIN configuration; restored cards and stations require the documented access review.

Server update checks: When an administrator opens Carribrary, the server may check the public Carribrary GitHub releases API, normally no more than once a day. GitHub receives the server public IP address and a generic update-check user-agent. No library contents, borrower details, private links, configuration keys or signing credentials are included. Updates are not installed automatically.

Optional additional-library hosting
Each additional library has its own database, sign-ins, pairing credentials, data-protection keys and backups. Its content is not silently included in the main library backup. A private connection file authorizes encrypted access to another server’s existing public browser interface; keep it private and transfer it only to the intended administrator. Connection tokens and optional per-hostname DuckDNS tokens are protected at rest. DNS updates contact DuckDNS while the configured server is running. Public HTTPS still involves certificate authorities and public hostname records. No hosting registry, private connection file or library content is sent to Chezburber Studios.

Household reader app installation
A household reader may explicitly remember their personal-link capability in this browser profile or installed app’s local storage. It is off by default. Anyone using that profile can open the saved reading link; use a device lock and Forget saved reading link on shared devices. It is not included in public manifests, server request URLs or offline content caches. Browser/OS backups can retain device storage. Replacing or disabling the personal link on the server invalidates old links.
